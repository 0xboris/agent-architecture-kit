One screen, two slices

The notes UI knows only an author's id. The screen fills two gaps with users UI: it hands the current user's id to NewNoteForm, and it passes renderAuthor so NotesList can show a name without knowing what a user is.

apps/web/src/screens/notes/NotesScreen.tsx
// imports from both public entries and shared UI
import { NewNoteForm, NotesList } from '../../features/notes/ui/index.ts';
import { CurrentUser, UserName, UserSwitcher } from '../../features/users/ui/index.ts';
import { Page, Section } from '../../sharedui/Page.tsx';

export function NotesScreen() {
  return (
    <Page title="Notes" actions={<UserSwitcher />}>
      <CurrentUser>{(user) => <NewNoteForm authorId={user?.id} />}</CurrentUser>
      <Section title="All notes">
        <NotesList renderAuthor={(authorId) => <UserName userId={authorId} />} />
      </Section>
    </Page>
  );
}

One rule, checked three times

The rule "only the author may edit" is canEdit in the shared domain. The web app uses it twice to avoid asking for an edit the API would refuse. The API checks the rule too, and its answer decides.

What I noticed

What works

  • The slices stay apart in every layer of both apps, and the check enforces it.
  • Each screen is the only place that joins slice UI. The notes UI takes an id and a render function, not a user, so it would work with any author display.
  • Rules that both apps use exist once. parseUserName, usersByName and canEdit are in packages/domain.
  • The migration adds a user only when old notes exist and assigns them to it, so a filled database migrates without errors. It has its own test.
  • The glossary names User, User name, Current user and Author, including the missing sign-in.

Worth a decision

  • Slice UI links to app routes: NotesList to /notes/$noteId, UserSwitcher to /users. The paths are typed through routes.tsx, so slice UI depends on the composition root in a way the check can't see. A screen could pass the link in instead.
  • The kit doesn't describe the render-slot pattern (renderAuthor, the CurrentUser render prop). The other session invented it. It belongs in the kit's TypeScript guide so the next slice copies it.
  • The kit doesn't say that a use case may read another slice's port, as CreateNote reads UserStore. It is allowed, because ports belong to the app, not the slice. One line in docs/ARCHITECTURE.md would settle it.
  • The notes routes define the x-user-id header. It moves to sharedui/http.ts when a second slice writes as the current user, and becomes a port when sign-in arrives.
